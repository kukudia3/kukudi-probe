# 性能验证（Phase 11）

本文记录**实测数字**、测量方法、以及由数字得出的结论与调整。
所有测量都能复现：`make bench`（Go 基准）、`make load`（50 节点负载用例）、
以及 `deploy/` 之外的压测工具 `fakeagent`（见文末"复现步骤"）。

> 测量机：Windows 10 x64（28 逻辑核）。**Windows 上的 RSS 通常高于 Linux**
> （Go 运行时 + 驱动在 Windows 上的驻留页更多），因此下面同时给出"增量"，
> 增量与平台无关，更有参考价值。

## 1. 设计预算 vs 实测

| 指标 | 设计预算（`DESIGN.md` §14） | 实测 | 结论 |
|---|---|---|---|
| Server RSS（50 节点 @1 Hz） | ≤ 80 MB | **稳态 37–39 MB**（10 分钟长跑，Windows） | ✅ 达标（预算的一半） |
| Server CPU（50 帧/秒） | < 3% 单核 | 30–60 秒窗口内低于计数器分辨率（< 0.05%） | ✅ 远低于预算 |
| Agent CPU（1 秒一采样） | < 0.3% 单核 | **108 µs/次采样**（≈ 0.011%） | ✅ 达标 |
| Agent RSS | ≤ 20 MB（预期 8–15 MB） | 采样路径堆占用 0.64 MiB；10000 次采样后堆变化 **−24 KB** | ✅ 无累积状态 |
| 写库频率 | 个位数事务/分钟 | **6 次/分钟**（10 秒一批样本），另有每分钟 1 次运行态+流量 | ✅ 达标 |
| 前端每秒推送量 | 10–15 KB/s（估算） | **约 40 KB/s**（50 节点每秒全变） | ⚠️ 见 §4，已做优化 |

## 2. 50 节点负载实测（真实二进制 + 50 条 WebSocket 连接）

### 2.1 10 分钟长跑（Phase 13，稳态数字最有参考价值）

```
第  1 分钟  RSS  108.3 MB  CPU 0.0s  在线 50/50  1h点数   6  DB     4 KB  WAL 1,927 KB
第  2 分钟  RSS  128.5 MB  CPU 0.0s  在线 50/50  1h点数  12  DB     4 KB  WAL 2,305 KB
第  3 分钟  RSS   37.0 MB  CPU 0.0s  在线 50/50  1h点数  18  DB     4 KB  WAL 2,865 KB
  …（中间略）…
第 10 分钟  RSS   39.4 MB  CPU 0.0s  在线 50/50  1h点数  60  DB   356 KB  WAL 4,144 KB
```

- **稳态 RSS ≈ 39 MB**（Windows）。前两分钟的 108→128 MB 是启动时堆增长 + 首次落盘的一次性开销，
  Go 的 GC 在第三分钟把内存还给了操作系统，之后 8 分钟一直稳定在 37–39 MB（±2 MB）。
  早期另一轮测量里出现过的 96–116 MB 是**爬坡期**的瞬时值，不是稳态。
- CPU 在 30 秒/60 秒窗口内都低于 Windows 计数器分辨率（0.0s）→ 50 帧/秒的负载对 CPU 几乎无感。
- 数据库在稳定增长（356 KB 主库 + 4 MB WAL，WAL 到阈值自动 checkpoint），
  10 分钟 50 节点的历史只有几百 KB —— 保留策略（12h/8d）下不会失控。
- 日志里只有 1 条 WARN（首次启动打印初始化码），**零 ERROR**。

### 2.2 单次接口延迟与内存增量（另一轮测量）

```
基线（0 节点、0 连接）      RSS  79.2 MB   线程 15
50 个节点已建（无连接）      RSS  81.8 MB   （+2.6 MB）
50 条连接、25 秒后           RSS  96.5 MB   （+14.7 MB，含爬坡）
上报速率                     50 帧/秒，失败 0
```

| 接口 | 实测延迟 | 返回大小 |
|---|---|---|
| `GET /api/v1/nodes`（50 节点列表） | **1.24 ms** | 46 KB |
| `GET /api/v1/nodes/1`（详情） | 1.01 ms | — |
| `GET /api/v1/nodes/1/series?range=1h`（360 点） | 0.89 ms | 238 B（无数据时） |
| `GET /api/v1/nodes/1/series?range=7d` | 0.90 ms | — |

数据库在运行中是 `probe.db` + `probe.db-wal`（WAL 会在约 1000 页时自动 checkpoint），
所以主库文件大小是"滞后"的，这是 SQLite 的正常行为，不是数据没落盘。

### 2.3 硬杀恢复（kill -9）

```
杀前：DB 356 KB，WAL 4,144 KB
kill -9（Stop-Process -Force，无优雅退出）
重启后：节点 50 个、历史 1h 60 点 / 12h 9 点（rollup 生效）、
        今日与本月流量 623,902,720 字节、审计可读、stderr 为空
```

结论：`synchronous=NORMAL` + WAL 下，**硬杀不丢已提交数据**；
最多丢最后 10 秒还在内存里的样本桶（这是设计里明确接受的取舍，见 §8）。

## 3. Go 基准（`make bench`）

```
# Agent（testdata 里的 /proc 快照）
BenchmarkCollectorSample-28     5000   107908 ns/op    8789 B/op    83 allocs/op
BenchmarkCollectorInfo-28       5000       54.8 ns/op     3 B/op     0 allocs/op

# 服务端（50 个节点、每节点 1 小时历史 / 30 天流量）
BenchmarkCurrentNodes50-28      2000   149683 ns/op   99220 B/op   1056 allocs/op
BenchmarkSeriesQuery1h-28       2000   254467 ns/op   27752 B/op   1457 allocs/op
BenchmarkTrafficAggregates50-28 2000   832251 ns/op  320908 B/op   7871 allocs/op
BenchmarkEncodePayload50-28     2000    80820 ns/op   41205 B/op      3 allocs/op
```

- `currentNodes`（50 节点：查配置 + 汇总流量 + 组 DTO）**150 µs**，每秒只调用一次 → 0.015% 单核。
- `trafficAggregates`（50 节点 × 30 天日流量）**832 µs**，同样每秒一次 → 0.08% 单核。
  这就是"用 2 次查询喂 N 个节点"的价值：如果按节点查，50 个节点就是 150 次查询。
- 曲线查询 **254 µs**（360 个点，含 SQL 聚合），手机端滑动切换范围时毫无压力。
- 变更集编码 **81 µs / 3 次分配**（`json.Marshal` 一次成型，没有中间结构）。

**Agent 内存的关键证据**（`TestSampleSteadyStateMemory`）：跑 10000 次采样后
堆占用从 0.66 MiB 变成 0.64 MiB（**减少** 24 KB）。也就是说采样路径没有任何累积状态，
RSS 稳态基本等于 Go 运行时的固定开销 + 峰值临时分配。

## 4. 发现的问题与处理

### 4.1 SSE 每秒推送量是估算值的 3 倍（40 KB/s）→ 已优化

实测：50 个节点每秒都变化时，每个浏览器每秒收到约 **40 KB**（变更集 40.8 KB + 汇总），
15 秒窗口共收到 738 KB。设计文档里的估算是 10–15 KB/s（按每节点 ~250 字节），
实际每个节点 DTO 约 800 字节（含磁盘数组、流量、可用率等 30 个字段）。

- 对桌面浏览器完全无所谓（40 KB/s ≈ 0.3 Mbit/s）；
- 但**手机后台标签页**一直收这个量意味着每月数 GB 流量，这与"低资源"的原则冲突。

**处理（已实现）**：前端在 `visibilitychange` → hidden 时**主动断开 SSE**，回到前台再重连并
重新拉一次全量快照。后台标签页的流量降为 0，且不牺牲任何正确性（重连时拿到的是最新全量）。
进一步压缩 DTO（增量字段、短键名）留到 v1.1，因为收益（40 → 20 KB/s）小于复杂度。

### 4.2 每 IP 连接上限挡住了"同机 50 节点"压测 → 已改为可配置

压测时 50 条连接里 30 条被 429 拒绝（默认每 IP 20 条）。这在**真实场景**里也可能是问题：
多台 VPS 在同一 NAT/反代后面时，它们对服务端看起来是同一个 IP。

**处理**：新增 `--agent-max-per-ip`（默认 20）与 `--agent-max-conns`（默认 500），
并在启动时校验"每 IP ≤ 总数"。压测与负载用例把它们调大。

### 4.3 第二轮全量走查改掉的效率问题

| 问题 | 原来 | 现在 |
|---|---|---|
| 1 Hz 循环每秒对 `traffic_daily` 做全表 GROUP BY（只增不减的表） | 每秒 2 次聚合查询，随天数线性变慢 | 汇总结果按分钟缓存 + 落盘/增删节点后立刻失效（`traffic_cache.go`），显示值不变 |
| 1 Hz 循环每秒取整张 `traffic_daily`（`WHERE day >= ?` 用不上主键前缀） | 每秒物化最多 62 天 × 节点数的行 | 同上：每秒路径不再碰历史表 |
| rollup 每分钟重算 2 小时窗口，且不带 `node_id` 条件（退化成整表扫描） | 每个 1 分钟桶被反复重写上白次 | 稳态只重算最近 10 分钟；按节点逐条执行（走主键区间）；启动时仍回补 2 小时 |
| 每个已鉴权请求都写一次会话续期 UPDATE（落在唯一写连接上） | "每分钟个位数事务"变成"每请求一次写"，与采样落盘抢锁 | 续期节流为每分钟最多一次（TTL 语义不变） |
| 前端资源没有 ETag（`go:embed` 没有修改时间） | 每次导航重新下载约 77 KB | 内容 ETag + `If-None-Match` → 304、0 字节（真实二进制实测） |
| Agent 上报限流把控制帧也算进配额 | 心跳稍密就可能开始丢真实数据 | 只对上报帧计配额（`TestAgentRateLimitOnlyCountsMetrics`） |
| 超速丢弃时每帧一条 WARN | 一个刷帧客户端能刷爆日志与磁盘 | 只记第 1 次与之后每 100 次 |

数据正确性方面同时修掉：可用率在"上报间隔 > 10 秒"时恒为 `—`（`all_cnt` 整数除法归零 → 引入 `uptimeScale = 600`）、
`rollup` 少算最后一个已封闭桶、保留策略先删源行时残缺结果覆盖完整 1 分钟行、
`snapshot→commit` 之间到达的流量被清零丢弃、以及"删除/停用节点后残留帧毒化整批落盘（外键失败）"。

### 4.4 没有发现的问题

- 50 帧/秒下**零丢帧、零序号跳变**（`TestFiftyAgentsLoad`：1199/1200 帧处理成功，1 帧是收尾时序）。
- goroutine **16 → 16**：连接关闭后没有泄漏。
- 50 节点列表 1 ms 级返回（预算 100 ms）。

## 5. 复现步骤

```bash
# 1) Go 基准（Agent 采样 + 服务端查询）
make bench

# 2) 50 节点负载用例（真实 WebSocket 连接，约 200 帧/秒，跑 6 秒）
make load

# 3) 真实二进制的端到端压测（需要压测工具，见下）
make release
# 在服务端上：./probe-server --listen 127.0.0.1:25774 --data-dir ./data --log-level debug
# 建 50 个节点并保存各自的 Token 到 tokens.txt，然后：
fakeagent -server http://127.0.0.1:25774 -token-file tokens.txt -bind 127.0.0 -interval 1s -duration 120s
# 观察 RSS / CPU（Windows: Get-Process；Linux: pidstat -r -u -p <pid> 1）

# 4) 落盘节奏（debug 日志里每次样本落盘一行）
journalctl -u probe-server | grep buckets= | wc -l   # 除以运行分钟数
```

`fakeagent` 是一个约 250 行的小工具（不在本仓库内）：它按协议握手、按间隔上报、
每条连接可绑定不同的本机地址（模拟"50 台不同 VPS"）。它的用途就是 Phase 11 的测量
与告警链路的真实断线验证。

## 6. 结论

- 设计预算（§14）全部达标，且关键路径有 **10 倍以上余量**：
  1 秒一次的"查配置 + 汇总流量 + 编码推送"合计约 **1 ms 的 1/1000 单核**。
- 真正需要盯的不是 CPU，而是**每浏览器的推送量**：已用"后台断开"把它控制住。
- 长期运行的隐患只剩两个，都已在 Phase 13 覆盖：
  数据目录大小（保留策略 + 每小时清理）与 SQLite WAL 的自动 checkpoint。
